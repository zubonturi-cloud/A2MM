# Using the 6522 VIA Timer  

## Timer1 One-Shot Mode  

For applications involving the ALF "PERFORM" program, using Timer1 in one-shot mode is the simplest approach.  
For example, during the initialization phase, configure the Timer1 mode as follows:  
```text
LDA	#$FF
STA	$C0D2	; DDRB OUTPUT
STA	$C0D3	; DDRA OUTPUT
;
LDA	#$80
STA	$C0DB	; Timer 1 one-shot mode with PB7 output for esay debug
```
Then write the timer count value corresponding to one "tick" into the 6522 timer registers:
```text
LDA	#$AB	; for example setting #$CDAB
STA	$C0D4
LDA	#$CD
STA	$C0D5	; Set timer value and start counting
```
After completing the necessary processing of envelopes and commands, wait for the next tick:
```text
WAIT BIT  $C0DD   ; Test IFR
     BVC  WAIT    ; Count has not yet reached zero
```
By polling in this manner, you can implement tempo control via the timer without requiring significant modifications to the "PERFORM" program.

## Timer1 Free-Run Mode  

If you must use free-run mode, you must enable the T1 interrupt via the IER (Interrupt Enable Register) for it to function correctly.
```text
LDA	#$FF
STA	$C0D2	; DDRB OUTPUT
STA	$C0D3	; DDRA OUTPUT
;
LDA	#$80
STA	$C0DB	; T1 one-shot mode, with PB7 output
STA	$C0D4	; Set low byte of counter
STA	$C0D5	; Set high byte of counter and start counting
;
STA	$C0DE	; Enable T1 interrupt
```
In free-run mode, you must pre-configure a routine to handle interrupts generated by Timer1.
The Apple II RAM contains a vector at a specific address where you can set a callback routine to be executed upon an interrupt.
```text
03FE:ISRL
03EE:ISRH
```
Within an interrupt service routine (ISR), you must perform only the bare minimum of processing—such as setting a flag—before returning.
```text
ISR: PHA
     LDA $C0D4 ; reset IFR
;
; do some flag work here
;
     PLA
     RTI
```
In this case as well, within the `PERFORM` program—much like in One Shot mode—the approach would involve checking this flag during the polling process that waits for one tick to elapse.  
This method has the advantage that processing delays do not accumulate from one tick to the next. (However, this level of precision might be excessive for this purpose.)

### Stop and Re-enable interrupt
To disable interrupts, write the following to the VIA's IER register:
`C0DE:40`

To re-enable (restart) them, write:
`C0DE:C0`

## The issue with "SUGGESTED SPEED" and "TEMPO"  

When playing music files created within the ALF system on a platform other than ALF, there is an issue that must be considered regarding how the playback speed is determined: specifically, how to handle "Suggested Speed" and "TEMPO."  

### Suggested Speed  
"Suggested Speed" is a one-byte speed parameter specified in most ALF music files. This value corresponds to a setting derived from an Apple II game paddle, with each unit representing 10.7 microseconds.  
The value typically ranges from approximately 150 to 255; when multiplied by the unit, this results in a duration of 1.6 to 2.7 milliseconds per "tick" of the ALF music.  
If this parameter is present in a music file, the playback will pause at the start, requiring the user to adjust the game paddle.  
If this value is set to 0, no pause is inserted, and playback begins immediately, regardless of the state of the game controller.

### TEMPO
"TEMPO" is a command for the MC16 system that can be used optionally within ALF music files.  
Like "Suggested Speed," this command alters the duration of a single "tick"; however, while "Suggested Speed" serves merely as an instruction for the user, the "TEMPO" command directly modifies the program's execution.  
The value is an unsigned 16-bit integer, with each unit representing approximately 0.561 μs.  
When this command is executed during playback, the PERFORM program applies the effect by overwriting a portion of its own code with the parameter provided by the command.

### VIA's built-in timer  
The VIA’s built-in timer is a 16-bit counter that uses the Apple II’s system clock (approximately 1.023 MHz) as its primary oscillation source.  
While it is technically possible to support configurations based on either paddle values ​​or TEMPO commands, bridging the two given their differing time bases requires some form of conversion process to be applied to the count values.
For the "Suggested Speed" setting, using a pre-calculated conversion table is an appropriate solution; since this conversion only needs to be performed once before playback begins, it is not particularly complex.  
Conversely, because TEMPO parameter conversions may occur during actual playback, the process must be done as quickly as possible. Furthermore, since TEMPO command parameters are 16 bits wide, they must be converted via calculation rather than by using a lookup table.
While it is possible to pre-emptively rewrite TEMPO parameters to their converted values—a method I have encountered in existing files—doing so comes at the cost of compatibility of that song data with other systems. That said, depending on one's perspective, this simple approach might be considered the best solution.  
Furthermore, additional logic is required—such as reading the "Suggested Speed" before playback begins to configure the timer (thereby bypassing the need for user input) or patching TEMPO commands to automatically trigger the conversion routine.
